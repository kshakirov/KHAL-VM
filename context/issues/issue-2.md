## Архитектурное уточнение к Issue #2 — `TypeTag + union Payload`

После обсуждения уточняем первый эксперимент с tagged values.

### Решение

Для первоначальной реализации машинное значение KHAL представляем явно:

```cpp
enum class TypeTag {
    INT,
    BOOL,
    NIL
    // остальные теги добавляются по мере необходимости
};

union Payload {
    int64_t integer;
    bool boolean;
};

struct Value {
    TypeTag tag;
    Payload payload;
};
```

`TypeTag` является **единственным дискриминантом значения**.

Не используем `std::variant`, поскольку он содержит собственную информацию об активной альтернативе. В таком случае получились бы два независимых механизма типизации:

```text
KHAL TypeTag
+
std::variant discriminator
```

Для текущего эксперимента это нежелательно: проверяем именно механизм tagged values самой KHAL.

### Инвариант

Смысл `Payload` определяется `TypeTag`:

```text
INT  → payload.integer
BOOL → payload.boolean
NIL  → значимый payload отсутствует
```

Следовательно, операция машины должна сначала проверить tag и только затем обращаться к соответствующему полю `union`.

Будущая операция типа:

```text
ADD_INT r1, r2 → r3
```

семантически выполняет:

```text
r1.tag == INT
r2.tag == INT
        ↓
прочитать integer payload
        ↓
сложить
        ↓
r3 = { INT, result }
```

Таким образом, допустимость операции определяется состоянием самой KHAL, а не типовой системой C++.

### Граница решения

`union` **не объявляется окончательным физическим представлением KHAL**.

Это прозрачная реализация первого семантического эксперимента:

```text
Value = Tag + Payload
```

Размер tag, размер payload, packing, alignment, NaN-boxing, pointer tagging и отображение на реальные аппаратные регистры относятся к будущему этапу lowering и сейчас не фиксируются.

### Ближайшая цель Issue #2

1. Ввести `TypeTag`.
2. Ввести `Payload`.
3. Ввести `Value = TypeTag + Payload`.
4. Создать register file из 256 значений.
5. Проверить запись и чтение как минимум `INT`, `BOOL` и `NIL`.
6. Не вводить арифметику и формат bytecode до проверки этого базового машинного состояния.

## Что я проверил после первого прорыва

Я поднял свежий код, собрал его обычным Makefile и отдельно прогнал компилятором с `-Wall -Wextra -Wpedantic -Wconversion`. Сборка проходит чисто. На рабочем маршруте регистры `R1` и `R2` получают целые значения `222` и `333`, а `ADD_INT` читает их как `INT` и вычисляет `555`.

Что уже действительно сделано по новому смыслу тикета:

- появился `enum class Tag { INT, BOOL, NIL }`;
- появился явный `union Payload`;
- регистр состоит из `Tag + Payload`;
- внутри VM создан файл из 256 регистров;
- `LOAD_INT` одновременно записывает тег и integer payload;
- перед чтением в `ADD_INT` я проверяю оба тега через временный `assert`.

То есть главный эксперимент уже ожил: тип значения находится в состоянии самой KHAL, и операция смотрит на этот тип до чтения payload.

Но закрывать тикет я пока не хочу. Осталось честно добить границы эксперимента:

1. Сейчас реально пройден только путь `INT`. Для `BOOL` и `NIL` ещё нет проверяемой записи и чтения.
2. Массив регистров создаётся неинициализированным. Пока безопасны только явно загруженные `R1` и `R2`; для остальных ещё нет гарантии начального `NIL`.
3. `assert` годится как первый щуп, но исчезает в release-сборке. Позже машине понадобится собственное наблюдаемое состояние ошибки типа.
4. Индекс регистра и количество операндов инструкции пока не проверяются.
5. В `Payload` integer сейчас `int32_t`; это допустимо для опыта, но не надо случайно принять за окончательный размер машинного значения.
6. Старые пункты про `FIXED`, `RATIONAL` и битовую упаковку сознательно не выполнены: после архитектурного уточнения они относятся к будущему отдельному эксперименту.

Мой вывод: **семантическое ядро Issue #2 реализовано для `INT`, а общий инвариант `INT/BOOL/NIL` ещё не завершён**. Ближайший чистый шаг — определить начальное состояние всех 256 регистров и отдельно доказать запись/чтение `BOOL` и `NIL`, не добавляя новых типов.
