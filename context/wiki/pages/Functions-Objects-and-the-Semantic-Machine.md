# KHAL-VM — Functions, Objects and the Semantic Machine

## Куда мы идём

Следующий этап KHAL-VM — переход от элементарной арифметической машины к функциям и объектам.

Цель — не реализовать набор возможностей JavaScript и не копировать архитектуру V8.

Мы хотим построить **минимальную явную математическую модель**, из которой JavaScript-подобные свойства возникают естественно.

Общая линия исследования:

```text
Language semantics
        ↓
KHAL semantic machine
        ↓
KHAL representation
        ↓
lowering
        ↓
physical ISA / memory
```

Сначала определяется смысл сущности.

Потом — её представление в KHAL.

И только после этого исследуется эффективное физическое представление.

---

# 1. Текущая точка

Первый арифметический контур уже работает.

```text
LOAD_INT R1, 222
LOAD_INT R2, 333
ADD_INT  R1, R2
PRINT_INT R1
```

Семантика `ADD_INT` сейчас двухадресная:

```text
ADD_INT Ra, Rb
```

означает:

```text
Ra := Ra + Rb
```

Машинное значение представляется концептуально как:

\[
Value = Tag + Payload
\]

Тип является частью состояния самой KHAL.

Это достаточная опора для следующего эксперимента. Не нужно превращать первый этап в бесконечную полировку арифметики.

---

# 2. Главный принцип нового этапа

Не спрашиваем:

> Как реализовать JavaScript в C++?

Спрашиваем:

> Какие минимальные математические сущности необходимы машине, чтобы выразить нужную семантику?

Каждая новая сущность должна появляться только тогда, когда конкретный эксперимент доказывает её необходимость.

Никаких `Shape`, hidden classes, inline caches, NaN-boxing и других механизмов заранее.

Они могут появиться позже как результат исследования представления и lowering.

---

# 3. Функция

Первое приближение:

\[
Function = \langle CodeRef, Environment\rangle
\]

или, если окружение находится в памяти:

\[
Function = \langle CodeRef, EnvRef\rangle
\]

Функция содержит две принципиально разные вещи:

- код;
- окружение, необходимое этому коду.

Это гипотеза, которую нужно проверить экспериментами.

Не вводим заранее отдельные фундаментальные сущности `FUNCTION`, `CLOSURE`, `BOUND_FUNCTION`, если различие можно выразить состоянием окружения.

Но и не объединяем их заранее: общность должна быть доказана.

---

# 4. Environment

Минимальная математическая модель:

\[
Environment : Identifier \rightharpoonup Value
\]

То есть окружение — конечное частичное отображение имени в значение.

Например:

```text
a ↦ 2
b ↦ 3
```

Это уже даёт основу для параметров, локальных переменных и захваченных значений.

---

# 5. Объект

Первое приближение:

\[
Object : Key \rightharpoonup Value
\]

Например:

```javascript
let o = { x: 42 };
```

семантически соответствует:

\[
o = \{x \mapsto 42\}
\]

Чтение свойства:

\[
Get(o,x)=42
\]

Изменение:

\[
Set(o,x,7)
\]

Но для JavaScript важна ссылочная идентичность объектов.

Поэтому более сильный кандидат:

\[
Value ::= \ldots \mid ObjectRef(r)
\]

а состояние heap:

\[
Heap : Ref \rightharpoonup Object
\]

Тогда:

\[
Heap(r) : Key \rightharpoonup Value
\]

и

```javascript
a = o;
b = o;
b.x = 7;
```

естественно объясняется тем, что `a` и `b` содержат один `ObjectRef(r)`.

Никакого специального правила aliasing не требуется.

---

# 6. Object и Environment

Возникает важная исследовательская гипотеза.

Математически:

\[
Environment : Identifier \rightharpoonup Value
\]

и

\[
Object : PropertyKey \rightharpoonup Value
\]

очень похожи.

Возможно, это две специализации более общего примитива:

\[
Map : Key \rightharpoonup Value
\]

Но **пока их не объединяем**.

Их семантические роли различаются, и эксперимент должен показать, является ли различие фундаментальным или только специализацией общей структуры.

---

# 7. Вызов функции

Вызов следует рассматривать как переход состояния машины.

Условно:

\[
Call(\langle CodeRef,EnvRef\rangle,Args)
\rightarrow
Execute(CodeRef,Env',Args)
\]

Но вызов создаёт ещё одну важную сущность — состояние конкретного исполнения функции.

Функция и её invocation — не одно и то же.

---

# 8. Frame

Рабочая гипотеза:

\[
Frame =
\langle
Return,\ Registers,\ Args,\ Environment,\ Receiver
\rangle
\]

Точный состав ещё не фиксируется.

Главное различие:

```text
Function
    = постоянное значение / описание callable

Frame
    = состояние конкретного вызова
```

Одна функция может породить множество различных frames.

---

# 9. Регистровые фреймы

Текущий глобальный:

```cpp
Register registers[256];
```

был хорошим первым стендом.

Для функций естественным кандидатом становится собственное регистровое пространство каждого frame:

\[
Frame_i.Registers =
\{R_0,\ldots,R_{255}\}
\]

Тогда:

```text
R7 во frame A
```

и

```text
R7 во frame B
```

— разные элементы машинного состояния.

Машина постепенно начинает выглядеть как:

\[
Machine =
\langle Code, Frames, Heap\rangle
\]

где:

\[
Frames=[F_0,F_1,\ldots,F_n]
\]

Количество frames всегда конечно и ограничено реальными ресурсами машины.

Никакой физической бесконечности регистров не предполагается.

---

# 10. Calling Convention

Это ближайший практический шаг.

Важно:

> Calling convention — прежде всего контракт между вызывающим и вызываемым вычислением, а не физическая раскладка массива регистров.

На первом шаге не нужно вводить множество специальных регистров.

Минимальный кандидат:

```text
R0       — result
R1..Rn   — arguments / working registers
```

Например:

```text
caller:
    R1 = 2
    R2 = 3

callee:
    arguments = R1, R2
    result    = R0
```

Первый настоящий `CALL` покажет, какие дополнительные элементы действительно необходимы.

`SP`, `FP`, `ENV`, `THIS` и другие специальные роли не вводятся заранее.

---

# 11. Первый эксперимент с функцией

Начать следует с минимального случая:

```javascript
function add(a, b) {
    return a + b;
}

print(add(2, 3));
```

Этот эксперимент должен заставить нас определить только необходимые сущности:

```text
Function
CALL
arguments
Frame
local registers
RETURN
return value
```

Не добавлять объекты в этот же эксперимент.

Из него должна естественно возникнуть минимальная семантика вызова KHAL.

---

# 12. `this` и методы

После простого вызова можно перейти к объекту:

```javascript
let o = {
    x: 2,
    f: function () {
        return this.x;
    }
};

print(o.f());
```

Рабочая гипотеза:

метод **не является фундаментальной сущностью**.

Вместо этого:

```text
f = Get(o, "f")
Call(f, o, args)
```

или математически:

\[
Call(Function,Receiver,Args)
\]

Тогда `this` является receiver конкретного вызова, а не скрытым свойством функции.

Это необходимо проверить экспериментом.

---

# 13. Минимальная предполагаемая семантическая основа

Пока вырисовывается следующая система:

\[
Value
\]

\[
Ref
\]

\[
Heap : Ref \rightharpoonup Entity
\]

\[
Environment : Identifier \rightharpoonup Value
\]

\[
Object : PropertyKey \rightharpoonup Value
\]

\[
Function = CodeRef \times EnvRef
\]

\[
Frame
\]

и операции:

```text
Get
Set
Call
Return
```

Это пока исследовательская модель, а не окончательная ISA.

---

# 14. Semantic Machine и Physical Machine

Критически важно не смешивать уровни.

Семантическое значение:

\[
Value = Tag + Payload
\]

не означает конкретную физическую раскладку памяти.

Позже может исследоваться lowering:

\[
Value(Tag,Payload)
\longrightarrow Word_{64}
\]

Возможные реализации:

```text
explicit tag + payload
64-bit tagged word
pointer tagging
NaN-boxing
другая схема
```

Ни одна из них сейчас не является архитектурным обязательством.

---

# 15. 64-битные tagged values

Есть перспективная гипотеза о переходе к единому 64-битному машинному слову.

Мотивация:

- компактность;
- cache locality;
- дешёвое перемещение значений;
- потенциально естественный lowering на современные 64-битные ISA.

Но это **отдельный эксперимент представления**.

Сначала:

\[
Semantic\ Value
\]

затем:

\[
Representation
\]

и только затем:

\[
Physical\ Encoding
\]

NaN-boxing нельзя выбирать только потому, что он используется известными runtime.

KHAL должна прийти к физическому представлению из собственной модели и измерений.

---

# 16. Lowering

Если семантическая модель построена явно, lowering перестаёт быть набором специальных случаев.

Например:

\[
Function(CodeRef,EnvRef)
\]

может быть опущена в пару машинных ссылок.

\[
ObjectRef
\]

может стать адресом heap entity.

\[
Get
\]

может быть опущен в конкретный алгоритм lookup.

\[
Call
\]

может превратиться в конкретное соглашение о регистрах, frame layout и переход управления.

Главный принцип:

> При lowering меняется представление, но не смысл операции.

Поэтому желаемая цепочка проекта:

```text
JavaScript-like semantics
        ↓
KHAL semantic entities
        ↓
KHAL state transitions
        ↓
representation
        ↓
lowering
        ↓
x86-64 / ARM64 / other ISA
```

---

# 17. Что сейчас НЕ делать

Пока не нужны:

- prototype chain;
- classes;
- `new`;
- async/await;
- Promise;
- generators;
- hidden classes;
- shapes;
- inline caches;
- JIT;
- GC architecture;
- NaN-boxing;
- окончательная heap layout;
- окончательная binary encoding.

Каждая из этих сущностей должна появляться только после эксперимента, который покажет её необходимость.

---

# 18. Ближайший порядок работы

### Шаг 1 — Calling Convention

Поверх существующего регистрационного механизма определить минимальный контракт:

```text
arguments → registers
result    → R0
```

Не менять физическое устройство регистров больше необходимого.

### Шаг 2 — Function

Формализовать:

\[
Function=\langle CodeRef,EnvRef\rangle
\]

на простейшем `add(a,b)`.

### Шаг 3 — CALL / RETURN / Frame

Получить первый настоящий переход:

```text
caller
  ↓ CALL
callee frame
  ↓ RETURN
caller
```

### Шаг 4 — Object

Ввести:

\[
Object : Key \rightharpoonup Value
\]

и проверить `Get`/`Set`.

### Шаг 5 — Function inside Object

Проверить:

```javascript
o.f()
```

как композицию:

```text
Get + Call(receiver)
```

### Шаг 6 — только после этого Representation / Lowering

Исследовать, как получившаяся модель отображается на память и реальную ISA.

# Инструкция локальному Жене

Работать небольшими проверяемыми шагами.

Главная задача сейчас — не скорость реализации JavaScript-функций, а сохранение ясной причинной цепочки:

```text
необходимая семантика
        ↓
математическая сущность
        ↓
состояние KHAL
        ↓
инструкция
        ↓
реализация
```

**Не писать и не изменять код без прямой команды Паши.**

Фразы:

- «посмотри»;
- «проанализируй»;
- «оцени»;
- «что думаешь»;
- «предложи»;
- «давай обсудим»

не являются разрешением менять код.

При обсуждении новой возможности сначала определить:

1. какую семантическую проблему она решает;
2. можно ли выразить её уже существующими сущностями;
3. если нельзя — какая минимальная новая сущность необходима;
4. только после решения Паши переходить к реализации.

Не переносить архитектуру V8, JVM, CLR, Lua или другой VM в KHAL автоматически.

Они являются материалом для сравнения, а не шаблоном.

## Текущая непосредственная задача

Паша начинает с **calling convention регистров**.

Сначала нужно получить минимальный и понятный контракт вызова.

Не вводить заранее сложную систему frames, heap, object layout или 64-bit packing.

Первый критерий успеха:

> мы можем точно описать, откуда функция получает аргументы и куда возвращает результат.

После этого переходим к первому элементарному вызову функции.

# Исследовательский критерий

Успех этого этапа — не количество реализованных возможностей JavaScript.

Успех — если множество на первый взгляд сложных возможностей языка удастся получить композиционно из небольшого числа простых сущностей.

Идеальная KHAL должна объяснять сложность языка, а не повторять её внутри VM.
