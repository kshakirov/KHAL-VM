# KHAL-VM — Semantic Architecture and Experimental Directions

## Назначение

KHAL-VM — экспериментальная минимальная виртуальная машина.

Цель проекта — не воспроизвести существующую VM и не оптимизировать заранее выбранный язык, а исследовать цепочку:

**Language semantics → KHAL semantic machine → lowering → physical ISA**

Сначала определяется честная семантическая архитектура машины. Только после этого исследуется её отображение на x86-64, ARM64 или другое реальное железо.

KHAL имеет право быть необычной машиной, если необычность возникает из реальной семантической необходимости.

---

## Основной принцип

Каждая новая сущность должна появляться только тогда, когда существующей модели недостаточно.

Необходимо отличать:

- сложность самой задачи;
- сложность семантики языка;
- сложность виртуальной машины;
- сложность lowering;
- ограничения конкретной физической ISA.

Сложность не устраняется переносом между слоями. Поэтому KHAL старается помещать необходимую сложность именно туда, где находится её причина.

---

# 1. Tagged Values

Базовое машинное значение KHAL имеет форму:

```text
Value = Tag + Payload
```

`Tag` является частью состояния виртуальной машины, а не внешней метаинформацией runtime или компилятора.

Первоначально рассматриваются:

```text
INT
RATIONAL
STRING
SYMBOL
BOOL
NIL
REF / PTR
```

Возможные будущие значения:

```text
PAIR
OBJECT
FUNCTION
CLOSURE
BOUND_FUNCTION
CODE
CONTINUATION
```

Последний список не является утверждённой архитектурой.

Это направления для экспериментов.

---

## Почему Tag находится в машине

Обычная физическая машина видит преимущественно битовые последовательности.

KHAL исследует другой вариант:

> машина непосредственно различает классы значений.

Таким образом, регистр KHAL содержит не просто некоторое количество битов, смысл которых определяется внешним кодом, а семантически различимое машинное значение.

Это позволяет исследовать одновременно:

- Lisp-подобную tagged architecture;
- динамические значения JavaScript-подобных языков;
- typed interpreter;
- машинную типизацию;
- связь между типом и допустимыми переходами состояния.

---

# 2. Прямое представление прежде оптимизации

На первом этапе представление должно быть максимально прозрачным.

Не используются преждевременно:

- NaN-boxing;
- pointer tagging;
- compressed pointers;
- сложное bit packing;
- скрытые runtime representations.

Условная первая модель:

```text
Register
    Tag
    Payload
```

может быть физически неэффективной.

Это допустимо.

Сначала исследуется семантика машины.

Оптимизация представления относится к следующему этапу — lowering.

---

# 3. Semantic Machine и Physical Machine

Необходимо строго различать два вопроса.

### Semantic architecture

Что представляет собой значение KHAL?

Какие существуют состояния машины?

Какие переходы между ними допустимы?

Какие операции являются естественными примитивами?

### Lowering

Как это состояние реализовать на:

```text
x86-64
ARM64
RISC-V
...
```

Если операция KHAL требует нескольких операций реального CPU, это ещё не означает, что операция ошибочна.

Это может быть измерением расстояния между двумя архитектурами.

---

# 4. Язык не задаётся заранее

KHAL не проектируется как:

```text
Scheme VM
JavaScript VM
Rust VM
Curry machine
```

Вместо этого свойства различных языков используются как экспериментальные зонды.

Интерес представляют, в частности:

### Lisp / Scheme

- symbols;
- pairs;
- closures;
- first-class functions;
- continuations;
- tagged objects.

### JavaScript

- динамические значения;
- функции как значения;
- closures;
- bound functions;
- динамические objects;
- prototype-like mechanisms;
- shape-like information.

### Rust-like languages

- явные representation constraints;
- value semantics;
- references;
- типовая дисциплина;
- возможность контролируемого lowering.

Цель:

> определить, какие языковые конструкции естественно следуют из архитектуры KHAL, а какие требуют сложной надстройки.

---

# 5. Гипотеза: вызываемые значения

Одна из ближайших экспериментальных областей — функции.

На первом этапе предлагается **не объединять заранее** различные виды вызываемых значений.

Рабочие сущности:

```text
FUNCTION
CLOSURE
BOUND_FUNCTION
```

## FUNCTION

Минимальная функция может быть представлена как ссылка на исполняемый код:

```text
FUNCTION = CodeRef
```

Это пока только рабочая гипотеза.

---

## CLOSURE

Замыкание требует кроме кода некоторого окружения:

```text
CLOSURE = CodeRef + EnvRef
```

`EnvRef` предоставляет доступ к связанным значениям.

Физическое устройство окружения пока не определяется.

---

## BOUND_FUNCTION

JavaScript-подобная связанная функция может рассматриваться отдельно:

```text
BOUND_FUNCTION =
    CodeRef
    EnvRef
    BoundThis
    BoundArgs?
```

Однако это намеренно **не считается окончательной моделью**.

После реализации необходимо проверить, является ли `BOUND_FUNCTION` самостоятельным машинным объектом или лишь частным случаем closure.

---

# 6. Гипотеза общей модели CALLABLE

После реализации отдельных сущностей следует проверить возможность сведения:

```text
FUNCTION
CLOSURE
BOUND_FUNCTION
```

к общей форме:

```text
CALLABLE = CodeRef + EnvRef
```

Тогда потенциально:

```text
FUNCTION
    EnvRef = NIL

CLOSURE
    EnvRef = captured lexical environment

BOUND_FUNCTION
    EnvRef = environment containing
             bound this and arguments
```

Это пока **гипотеза**, а не архитектурное решение.

Рабочий принцип:

> Сначала различать сущности, пока не доказана общая модель.  
> Объединять только после работающего эксперимента.

---

# 7. Тип и операция

Tagged architecture позволяет исследовать более сильную модель, чем обычная runtime-проверка типов.

Например, вместо:

```text
ADD r1 r2
```

с последующей проверкой tags можно рассматривать операцию семантически:

```text
ADD : INT × INT → INT
```

Для другой комбинации машинное правило перехода может просто отсутствовать.

Это направление связано с идеей typed interpreter и должно исследоваться отдельно.

Важный вопрос:

> насколько далеко можно опустить типовую семантику непосредственно в архитектуру машины, не превращая её в тяжёлый runtime?

---

# 8. JavaScript как источник экспериментов

KHAL не ставит целью реализацию JavaScript.

Интерес представляет другой вопрос:

> можно ли выбрать отдельные сильные свойства JavaScript и построить машину, на которой они являются естественными, а не компенсируются сложностью runtime?

Современные JavaScript engines вынуждены использовать механизмы вроде:

```text
hidden classes / shapes
inline caches
speculative optimization
deoptimization
tiered compilation
GC
```

KHAL может поставить обратный вопрос:

> какую структуру следовало бы дать самой машине, чтобы часть этой сложности не требовалось восстанавливать динамически?

Возможное будущее направление:

```text
Value = Tag + Shape + Payload
```

Это **только исследовательская гипотеза**.

Вводить `Shape` в архитектуру до появления конкретного эксперимента не следует.

---

# 9. Сравнение виртуальных машин

KHAL исследуется не изолированно.

Особенно интересны:

```text
Lua VM
BEAM
Warren Abstract Machine
Chez Scheme runtime
```

Они демонстрируют машины с выраженной собственной вычислительной идеей.

Для контраста полезны:

```text
JVM
CLR
V8
```

Здесь особенно интересен вопрос:

> куда архитектура переносит сложность?

Одну и ту же конструкцию желательно рассматривать по цепочке:

```text
Language
    ↓
VM primitive
    ↓
runtime cost
    ↓
lowering
    ↓
native ISA
```

Сравнение должно быть не только количественным.

Нас интересует происхождение механизмов.

---

# 10. KHAL как экспериментальная промежуточная машина

KHAL не должна превращаться в обычный compiler IR.

Она должна оставаться исполнимой машиной:

```text
state
registers
values
instructions
transitions
```

Именно это позволяет исследовать отображение одной вычислительной машины в другую.

В перспективе:

```text
source language
      ↓
normalization
      ↓
KHAL
      ↓
explicit transformation / lowering
      ↓
native representation
```

Для структурных преобразований потенциально интересен Refal.

Но frontend, EBNF и конкретный язык пока не являются приоритетом.

---

# 11. Синхронное ядро

Асинхронность пока не является частью архитектуры KHAL.

На первом этапе достаточно:

```text
fetch
  ↓
decode
  ↓
execute
```

Приоритет:

```text
registers
tagged values
references
arithmetic
functions
calls
returns
```

Позже можно исследовать, нужны ли машине собственные сущности вроде:

```text
CONTINUATION
SUSPEND
RESUME
```

Они не должны вводиться заранее.

---

# 12. Исследовательский метод

Для каждой новой идеи используется цикл:

```text
необходимость
    ↓
минимальная сущность
    ↓
рабочий эксперимент
    ↓
сравнение с другими VM
    ↓
lowering analysis
    ↓
оставить / изменить / удалить
```

Код не должен задним числом становиться архитектурным аргументом.

Текущая реализация — эксперимент над моделью.

Архитектура определяет код, а не наоборот.

---

# Текущее состояние

Зафиксировано:

```text
Tag + Payload
```

как базовая модель значения.

Исследуются следующие направления:

```text
FUNCTION
CLOSURE
BOUND_FUNCTION

CALLABLE hypothesis

typed operations

JavaScript-like semantic primitives

semantic-machine → physical-machine lowering
```

Они пока не являются окончательными решениями.

Главный открытый вопрос KHAL:

> **Какая минимальная, но достаточно выразительная семантическая машина позволяет языковым конструкциям быть естественными, а затем честно отображаться на реальное железо?**
